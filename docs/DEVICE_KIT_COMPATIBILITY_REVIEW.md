# 키트 등록 API 추가 전 호환성 검토 — v2.3.0 기준 기록

**이 문서는 2026-10-06의 역사적 기준 코드 검토 기록입니다.** 아래 커밋·행 번호·55개 테스트 결과는 당시 v2.3.0에만 해당합니다. 이후 v2.4.0에서는 개인정보 보관정책·동의 API와 r6 배포 템플릿을 추가했으므로 키트 구현 전 최신 코드에 대해 다시 검토해야 합니다. 키트 API 자체는 v2.4.0에서도 미구현·미배포입니다.

작성일: 2026-10-06. 검토 기준: GitHub main 커밋 `2dd4437`, 백엔드 v2.3.0.

결론은 **기존 통신과 공개 응답을 유지하는 별도 API로 추가할 수 있다**는 것입니다. 키트 등록은 가구와 물리 기기의 매핑을 저장하는 기능이며, 장비의 자동 설정이나 인증정보 이전 기능이 아닙니다. 아래 조건은 [프론트 전달용 명세](DEVICE_KIT_API_SPEC.md)에 반영했습니다.

당시 작업은 명세 작성과 로컬 코드 검토였습니다. 당시에는 신규 API 구현, GitHub 업로드, EC2 접속, 운영 DB 변경 또는 하드웨어 배포를 수행하지 않았습니다. 이 기록을 GitHub에 보관하더라도 실제 새 API가 운영 환경에서 정상 동작하거나 충돌이 없다는 검증 결과로 해석하지 않습니다.

## 1차 검토: 기존 프론트·기기 계약

| 현재 동작 | 충돌 가능성 | 명세에 반영한 조치 |
|---|---|---|
| owner 가입 시 기기 4대와 credential 생성 | 가입 요청에 키트 필수를 추가하면 기존 프론트 가입이 실패 | 가입 요청·응답 유지, 가입 후 별도 등록 |
| 고정 역할 ID로 인증·MQTT·UDP 결과·알림 처리 | `device_id`를 물리 번호로 교체하면 통신과 위치 대응 오류 | 역할 ID 유지, `hardware_id`는 표시용 메타데이터 |
| `ui_status`는 연결 상태 5개로 계산 | 새 등록 상태를 enum에 넣으면 프론트 상태 처리 오류 | 키트 상태는 별도 GET의 `status`로 제공 |
| `/households/current.onboarding`은 주소 등록 상태 | 키트 등록 단계를 추가하면 기존 화면 분기 변경 | 기존 응답 그대로, 키트 GET 별도 호출 |
| LED·연결 설정 변경은 `config_version` 증가 | claim이 설정을 초기화하면 최신 ESP32 설정과 불일치 | 등록 시 설정·통계·heartbeat·버전 모두 보존 |
| 기존 WebSocket은 연결·설정·알림 이벤트 전달 | 새 필드를 기존 이벤트에 섞으면 응답 계약 변경 | 기존 이벤트 유지, 등록 결과는 GET으로 복구 |

기기용 `/device/v1/config`, `/device/v1/heartbeat`, 내부 MQTT 상태·알림 API와 오디오 수신 형식은 변경하지 않습니다. 기존 미확인 알림 API와 LED 설정·회원 탈퇴 API도 요청·응답을 유지합니다.

등록하지 않은 새 가구의 기존 기기 API를 서버에서 새로 차단하지 않습니다. 프론트는 등록 안내를 제공할 수 있으나 이번 기능으로 기존 기기 권한 정책을 바꾸지는 않습니다. 실제 새 가구 설치에는 기존 방식의 credential, MQTT 계정·ACL 및 장비 설정 작업이 필요합니다. 이번 기능만으로 펌웨어가 새 가구를 자동 선택하지 않습니다.

## 2차 검토: DB·중복 등록·동시성

### 기존 가구 보호

가구 모델의 내부 기본값은 `legacy_registered`로 두고, 새 owner 가입에서만 `unregistered`를 명시해야 합니다. 필드가 없는 기존 가구는 읽을 때 기존 등록 가구로 해석하며 대량 마이그레이션으로 값을 강제로 넣지 않습니다.

등록 조건은 저장된 `device_kit_status`가 명시적으로 `unregistered`인 경우입니다. `attribute_not_exists(device_kit_status)`까지 등록 가능한 것으로 처리하면 기존 운영 가구가 새 키트로 바뀔 수 있으므로 금지합니다. 기존 가구 `home-b0d7a380b457`는 재등록 대상이 아닙니다.

### 저장 구조

core 테이블의 기존 `pk`/`sk`에 새 `KIT#`와 `HARDWARE#` 영역을 추가합니다. 현재 코드의 기존 키 prefix와 중복되지 않습니다. 별도 테이블이나 GSI는 필수 사항이 아닙니다.

키트 기본정보에는 코드 해시·재고 상태·구성 버전·귀속 가구·등록 시각을, 가구에는 키트 상태·번호·등록 시각을 기록합니다. 논리 기기에는 키트 번호·물리 번호만 추가합니다. 추가 등록자 사용자 ID는 보관하지 않습니다.

물리 번호별 전역 중복 방지 레코드는 키트 발급 시 조건부 생성하고, 등록 시에도 해당 키트·역할과 귀속 가구를 조건부 검증합니다. 키트 및 물리 번호 레코드에는 TTL을 사용하지 않습니다.

### 원자성과 재요청

단일 등록 트랜잭션은 키트 1개, 가구 1개, 논리 기기 4개, 물리 번호 레코드 4개를 갱신합니다. 한 키에 조건 확인과 갱신을 두 작업으로 넣지 않고, 각 갱신에 조건을 포함합니다.

- 가구: 활성 상태, 현재 owner 일치, 명시적인 미등록 상태
- 키트: 검증한 코드 해시·구성 버전 일치, 미귀속 상태
- 논리 기기: 기존 레코드 존재, 역할·종류 일치, 매핑 미설정
- 물리 번호: 해당 키트·역할 일치, 다른 가구 귀속 없음

동일 요청 재전송은 권한·코드 및 4대 매핑을 다시 확인하고 기존 결과를 반환하는 별도 멱등 경로로 처리합니다. 모든 요청에 새 시각을 덮어쓰거나 코드 해시를 삭제하지 않습니다.

메모리 저장소도 하나의 잠금 안에서 전체 검증 후 일괄 변경해야 합니다. DynamoDB의 기기 레코드는 전체 덮어쓰기 대신 키트 매핑 필드만 부분 갱신합니다.

등록 결과와 충돌 후 판별에는 강한 일관성 조회가 필요합니다. 여러 개별 조회 자체가 원자적 스냅샷인 것은 아니므로 가구와 기기 매핑 정합성을 검사하고, 중간 상태를 읽었다면 재조회합니다. 확인되지 않은 상태를 성공 또는 미등록으로 추측하지 않습니다.

## 3차 검토: 권한·탈퇴·운영

owner/member 및 타 가구 접근은 기존 권한 검사를 재사용합니다. 다른 가구의 키트 상태는 유효한 등록 코드를 확인한 뒤에만 오류로 알려주고, 없는 번호와 틀린 코드는 같은 오류로 처리합니다.

등록 코드용 Argon2id 함수를 기존 라이브러리로 별도 작성합니다. 현재 `hash_password()`는 비밀번호 10자 이상 정책을 적용하므로, 하이픈 포함 9자인 등록 코드에 그대로 쓰면 오류가 납니다. 미리보기와 등록 요청은 사용자·IP 제한을 공유하며 비밀값은 응답이나 로그에 남기지 않습니다.

owner 연동 해제·탈퇴는 현재와 같이 가구를 비활성화합니다. 등록된 키트와 물리 번호는 자동으로 해제하지 않습니다. 새 등록자 사용자 ID를 저장하지 않아 이번 기능 때문에 탈퇴 정리 대상인 사용자 참조가 추가되지 않습니다. 기존 계정 삭제 기능의 개인정보 처리 범위 전체를 새로 감사한 것은 아닙니다.

현재 IAM 템플릿에는 `GetItem`, `Query`, `PutItem`, `UpdateItem`, `TransactWriteItems` 등 필요한 동작이 포함돼 있습니다. 다만 이번에 EC2의 실제 적용 정책과 key-prefix 조건은 확인하지 않았으므로 스테이징에서 확인해야 합니다. 이전에 `Scan`이 성공했다는 사실만으로 새 키 영역의 전체 권한을 보장할 수는 없습니다.

기존 Nginx는 `/v2/` 전체를 전달하고 CORS는 POST를 허용하므로 새 경로만을 위한 라우팅 변경은 필요하지 않습니다. 별도 `Idempotency-Key` 헤더는 요구하지 않습니다. 단일 worker용 현재 요청 제한 방식은 여러 worker로 확장하면 공유 저장소 방식으로 교체해야 합니다.

검토 당시 systemd 템플릿에는 `/opt/hearo-backend-v2-r4` 경로가 남아 있었습니다. 실제 운영은 전달받은 배포 로그 기준 r5이므로 이를 그대로 복사해 r4로 되돌리지 않아야 합니다. 이후 v2.4.0용 r6 템플릿이 별도로 추가되었으며, 현재 배포에는 [v2.4.0 안내](DEPLOYMENT_V2_4.md)를 따릅니다.

## 구현 시 필요한 변경 범위

| 대상 | 추가할 내용 | 보존할 부분 |
|---|---|---|
| `domain.py` | 가구 내부 키트 상태, 기기의 선택적 물리 번호 | 기존 공개 응답 필드 |
| `schemas.py` | 입력 정규화·검증, 3개 API 응답 모델 | 기존 가입·설정 요청 모델 |
| `services.py` | 신규 가입 marker, 미리보기·등록·상태 조회 | 기존 기기 4대 생성과 credential 반환 |
| `store.py` | 재고 조회, 조건부 귀속, 원자적 메모리 처리 | 기존 credential alias와 부분 갱신 |
| `main.py` | 3개 경로, 권한·공유 요청 제한·오류 처리 | 주소 온보딩·기기 API·WebSocket |
| 관리자용 도구 | 키트 재고·4대 구성·중복 방지 레코드 발급 | 운영 장비 인증정보 자동 변경 금지 |
| 테스트 | 신규·legacy·경쟁·실패·멱등·회귀 검증 | 기존 테스트 삭제·약화 금지 |

명세 작성 단계에서는 위 구현 파일을 수정하지 않았습니다. 특히 사전 발급된 키트 재고가 없다면 올바른 API를 구현해도 등록할 제품이 없으므로, 관리자용 재고 등록 절차를 구현과 함께 준비해야 합니다.

## 검증 결과와 미검증 범위

- 당시 v2.3.0 기준 코드의 기존 테스트: **55개 통과**. 현재 v2.4.0 전체 테스트 수를 뜻하지 않습니다.
- 기존 회원·기기 계약, DB·동시성, 권한·탈퇴·운영을 나누어 3차 검토하고 검토 의견을 명세에 반영했습니다.
- 신규 API는 구현하지 않았으므로 API 호출·DynamoDB 등록 경쟁·실제 ESP32/Raspberry Pi 회귀 시험은 실행하지 않았습니다.
- 실제 EC2 IAM·DB 데이터·네트워크·CORS 및 프론트 등록 화면은 이번 검토에서 직접 확인하지 않았습니다.

기존 테스트 통과는 기준 코드가 정상이라는 근거이며 새 키트 API의 성공 근거는 아닙니다. 신규 기능의 필수 테스트는 명세의 “배포 전 완료 기준”에 별도로 기재했습니다.

## 안전한 후속 배포 조건

1. 별도 구현 브랜치에서 기능과 테스트를 추가합니다. 기존 가구 marker를 강제로 변경하지 않습니다.
2. 운영과 분리한 스테이징 테이블 및 테스트용 키트로 동시 등록·실패·탈퇴 시험을 수행합니다. 기존 운영 테이블을 공유하는 스테이징에서 실제 가구를 실험 대상으로 사용하지 않습니다.
3. 운영 코드·환경파일·서비스 파일·재고 변경 전 데이터를 백업하고 실제 실행 경로와 IAM을 확인합니다.
4. 구버전으로 롤백할 때 이미 등록된 귀속 레코드는 삭제하지 않습니다. 구버전이 만든 marker 없는 가구는 재배포 후 legacy로 분류되므로, 롤백 기간의 가입은 기록하고 별도 점검해야 합니다.
5. 신규 Swagger 경로, 프론트 요청과 응답, 기존 heartbeat·MQTT·LED·알림 기능을 검증한 뒤 프론트에 운영 연동 완료를 안내합니다.

이 명세는 키트 번호 입력만으로 실제 장비가 새 가구로 자동 연결되는 기능을 약속하지 않습니다. 자동 provisioning, 양도·교체 및 키트 재설정은 별도 개발 범위입니다.
